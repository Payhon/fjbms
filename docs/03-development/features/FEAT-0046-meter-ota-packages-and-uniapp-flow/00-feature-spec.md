## 2026-09-12 动态 ACK 时序（当前生效，取代下文历史时序）

- 三条 BLE 与 MQTT/4G OTA 的 0x50～0x53 首次 ACK 等待 800ms，超时立即同帧重发最多3次，每次等待450ms；取消220ms宽限。
- 0x53 保留设备游标、ACK进度与300ms跨页保护，无进展恢复预算从5次降为3次，回退/重新准备同样占用预算，仅超过确认高水位重置。
- 0x54 首发前仍等待300ms，首发等待5000ms，最多3次超时重发各等待450ms；取消BLE八次连发/6400ms窗口及重发前额外等待。
- 仅协议ACK超时重发；非超时错误立即结束。0x50及4G的0x51耗尽超时重试后保留继续兼容；严格完成ACK及限定BLE完成后断连兼容不变。
- 零宽限不调度Android超时读探测。普通连接12000ms超时、OTA后核验、MTU、连接恢复不变；真机验收前保持in_progress。

## 2026-09-10 已批准：BLE OTA 会话清理与自动恢复

- 原生断连同步失效 transport、缓存和当前页面通信状态；旧任务不得删除新连接。扫描退出关闭超时后保留同设备关闭屏障，不阻塞其他设备扫描。
- 三条 BLE OTA 在实际派发 Boot 请求后，结束时清理旧连接并自动恢复；30 秒总时限、最多两次连接、首次及重试前等待 1 秒。离开页面取消恢复，不自动重刷、不关闭全局蓝牙适配器。
- BMS 读取正常状态及实际版本，仪表自身查询仪表版本且不依赖 BMS。恢复结果与协议升级结果分开；失败保留手动重连入口。
- 数据时序、地址、完成条件和 MQTT/4G 不变；调试关闭不新增会话日志。未开始 Boot 的取消、下载失败不触发恢复。
- Android/iOS 微信小程序不退出进程连续透传升级各20次、弱信号和交替版本真机验证前保持 in_progress；不得将静态通过写成根因全部消除。

## 1. 背景与目标
- 当前 OTA 升级包管理与 UniApp 升级入口均围绕 BMS 设备设计，蓝牙仪表虽然走 Boot OTA 协议，但缺少独立的升级包管理和手动选包升级链路。
- 本次目标：
  1. 在 `ota_upgrade_packages` 中引入 `device_kind`，支持同表管理 BMS / 仪表升级包。
  2. 后台升级包管理页改为双 TAB，仪表升级包使用精简字段。
  3. UniApp 在蓝牙仪表详情页隐藏原 BMS OTA 检测入口，改为仪表专用“选包后升级”流程。
  4. 蓝牙仪表已透传连接 BMS 时，提供独立 BMS 升级入口，按现场 BMS 身份匹配后台固件并以 `0x01` 地址直接升级保护板。

## 2. 范围
### In Scope
- `backend/sql/51.sql` 为 OTA 升级包增加 `device_kind` 字段。
- `/api/v1/ota/package` 支持 `device_kind` 读写与分页过滤。
- 新增 `/api/v1/app/battery/ota/meter-packages` 返回仪表升级包全量列表。
- 后台 `升级包管理` 页面改为 `BMS 升级包 / 仪表升级包` 双 TAB。
- UniApp 设备详情参数页新增“仪表升级”卡片，仪表升级走手动选包 + `0xFC` Boot OTA。
- UniApp 仪表会话新增独立“BMS升级”卡片；点击后读取 BMS UUID，失败时按硬件型号降级匹配，并复用现有 BMS OTA 检查接口。
- 仪表透传 BMS OTA 固定使用 `0x01`，不使用仪表自身 OTA 的广播查询、跳过 `0x51` 参数；本轮数据阶段节奏由移动端共用。

### Out of Scope
- 不改 OTA 分包、CRC、Boot 帧格式。
- 不对仪表升级包做型号匹配或版本比较。
- 不新增第二张仪表升级包表。
- 本轮不修改 Bootloader；设备持续静默且重复包不返回当前游标时，客户端不能据此推断写入结果或承诺 100% 成功。

## 3. 验收标准
1. `ota_upgrade_packages.device_kind` 可区分 BMS(`1`) 与仪表(`2`) 包。
2. 后台升级包管理页可按 TAB 分别管理 BMS 与仪表包；仪表表单仅包含名称、文件、说明。
3. `/api/v1/app/battery/ota/meter-packages` 仅返回当前租户仪表升级包的 `id/name/description/package_url`。
4. UniApp 蓝牙仪表详情页隐藏旧 OTA Cell 与红点，显示“仪表升级”卡片。
5. 用户选择仪表固件并确认后，升级直接下载所选固件并按 `0xFC` 目标地址执行。
6. 蓝牙已连接但仪表尚未与后端 BMS 建立透传时，设备详情状态区可为空，前端不应无限重试读取状态；该场景仍须允许仪表升级。
7. BMS 升级卡片仅在蓝牙仪表会话显示；未读到 BMS 型号和版本时显示但禁用。
8. 点击 BMS 升级后才读取 UUID 和请求升级包，不在页面加载时新增 BLE/网络请求。
9. UUID、型号、批次约束沿用现有 BMS 选包优先级，并允许无约束通用 BMS 包兜底；所有查询受当前租户隔离。
10. 仪表透传 BMS 的首个 Boot 查询帧为 `55 FE 01 50 00 00 0C 39 FD`，后续流程与直接连接保护板一致。
11. 仪表自身、仪表透传BMS、直接连接BMS三条链路均以真实 `0x54 status=0` 为首选成功证据；仪表透传BMS必须收到该应答，直连BMS与仪表自身仅可使用第13条限定的完成后明确断连兼容。
12. 数据阶段采用设备 ACK 驱动：有效 `0x52` 应答后立即发送首个 `0x53`，普通数据包收到有效 ACK 后立即发送设备 `requested` 指定的下一包；每确认完成一整页 4KB 数据后，在发送下一页首包前固定等待 `300ms`。BLE 与 MQTT/4G 的 `0x50`～`0x53` 首次等待800ms，超时最多重发3次、每次450ms，无额外宽限。
13. 所有数据必须由设备 `requested == packetTotal` 完整确认后才能进入完成阶段；随后等待 `300ms` 发送真实 CRC32 的 `0x54`。BLE与MQTT/4G均首次等待5秒，ACK超时最多重发3次、每次450ms。匹配的 `0x54 status=0` 立即成功，非零状态立即失败；仅直连BMS或仪表自身的BLE会话，在“全部数据已确认且至少派发过一次 `0x54`”之后出现明确原生设备断连错误时允许兼容收敛。仪表透传BMS、普通超时、MQTT/4G断连及数据未完整确认均不得按成功处理。
14. Android BLE 的 MTU 协商仅作兼容性优化，不作为 OTA 成功的前提：API 不支持、失败或未返回数值时保留既有整帧写入容量并记录未知 MTU，不再假定成功请求值就是实际值；明确返回 MTU 低于 `78` 时仍在 Boot 前中止。数据包大小服从设备 `0x52` 返回档位，容量不足时明确失败，不擅自缩包或分片。
15. `0x53` Boot 帧必须由一次 BLE 写入完整发送，不允许分片；升级进度只在收到有效 `0x53` ACK 后按设备返回的 `requested` 更新。
16. 首包、中途、末包 `0x53` 首次800ms、重发450ms仍无ACK时必须重发同一包（无进展恢复预算最多3次），不能自行递增序号；同包重发达到有界上限仍无设备响应时失败。9月3日“超时跳到下一包、末包缺ACK也进入完成阶段”的试验规则已被失败日志证伪并撤销。
17. 设备 ACK 中的 `requested` 是数据发送状态机的唯一下一包游标：校验地址、命令、CRC、状态和范围后，主机按设备请求发送对应序号，不以本地发送次数推断设备已写入。`status=3` 同样按合法 `requested` 有界恢复；非法游标、反复无进展、设备拒绝、真实写入错误、断连和取消均必须失败。升级进度只按设备已确认游标更新，不因发送或超时提前增长。
18. BLE 与 MQTT OTA 全程暂停普通状态轮询并独占串行请求队列；成功、失败、取消后释放独占并恢复当前 Tab 策略。本轮仅共享Boot时序统一调整，普通通讯与连接恢复保持不变。
19. Android BLE 特征明确支持 `write` 时，`0x50`～`0x54` 必须显式使用带响应写，即使同时支持 `writeNoResponse`；仅不支持带响应写时使用无响应写。`writeNoResponse=false` 且 `write` 未明确为 `true` 时在 Boot 前失败；两项属性均缺失时仅为旧运行时兼容使用 `writeNoResponse` 并记录 `legacy-unknown`。Android响应写返回 `10007/property not support` 时，仅允许当前同一帧回退一次无响应写；iOS保持原写入策略。
20. Android 原生写回调不是 Boot 成功证据：pending 必须先于原生写建立，原生成功只用于诊断，协议推进仍只认有效 Boot ACK；ACK 先到后发生的迟到失败只记录，不得误伤下一请求。当前OTA宽限为0，不调度超时读探测，不延长ACK窗口。
21. Boot 期间日志只追加到有界内存，不逐条全量同步写缓存或刷新日志列表；每个 `0x53` 数据包保留一条包含 `seq/status/requested/RTT` 的紧凑结构化 ACK，完整十六进制只保留首包、末包、4KB 边界包、同包重试和异常。正常每包不新增冗余记录；仅在重试/超时时合并记录写模式、原生回调结果/耗时、RX字节数和限量解析错误。结束后统一发布和保存，手动复制可读取当前内存日志。

## 4. 风险与约束
- 仪表包与 BMS 包同表存储，历史 BMS 字段约束仍存在，因此仪表包需在服务层自动填充兼容值。
- 仪表升级包列表按租户全量返回，若同租户仪表固件较多，移动端选择体验依赖命名规范。
- 仪表临时会话没有可信 `device_id`；BMS 固件匹配必须使用现场 UUID/型号，禁止伪造设备ID或放宽租户边界。
- 新硬件 ACK 后主动等待仍受 `700ms` 时序约束；BLE 与 MQTT/4G 非完成帧应答窗口统一为 `450ms`，`0x53` 的 `220ms` 重发缓冲仍接收有效 ACK。MTU 未知的兼容路径不代表容量已验证，实际写入失败必须报错，不能推断升级成功。
- 旧版源码用于对齐 ACK 驱动、期待序号和整帧发送，不照搬未校验完成 ACK 的成功判定。Android/iOS、微信小程序/App、BLE 三条链路和 4G 真机验收前保持 `in_progress`。
- 9月3日超时推进试验已证明 ACK 丢失与设备未收到数据无法仅凭超时区分：跨页首包丢失后继续发送会形成不可恢复的序号空洞。现行规则固定重发同包，并由设备 `requested` 唯一推进；小程序定时器不是硬实时保证，仍须记录和验证实际670ms调度偏差。
- BLE完成后断连兼容只覆盖直连BMS或仪表自身、全部数据已确认、`0x54` 已至少派发一次后的明确原生重启断连；仪表透传BMS也不适用。它不是一般性的超时成功规则，最终仍需在真机验收中核对升级后版本变化。
- 日志延后保存避免影响收发，但进程被强杀时内存中的末段日志可能丢失；正常失败/取消/成功均需保存。仪表地址、广播查询、跳过 `0x51` 与9600准备参数不在本轮试验中盲目改写。
- `_resources/ble-upgrade-log-20260904-3-android.txt` 显示MTU 185、写容量182、帧长75、RSSI -45，包0～191均成功，包192在300ms页保护后初发及5次同序重发仍持续无可解析ACK；因此本轮排除MTU、分片、CRC、弱信号和跳包作为直接原因。300ms页保护与670ms同包重发继续保留，不能用更长固定等待或更多盲重试掩盖原生写/通知盲区。
- 若响应写已获得原生成功但同一包反复重发仍持续无RX，客户端已无安全依据继续推进。Bootloader要达到端到端可靠，必须在Flash完成后确认、对重复/旧序号始终返回当前 `requested`，并在回复 `0x54 status=0` 后再重启；该硬件门槛不因客户端本轮修复而关闭。

## 5. 回滚方案
- 回滚 `device_kind` 相关服务与前端调用。
- UniApp 回滚至现有 BMS OTA 入口逻辑，取消仪表升级卡片。
- 透传 BMS OTA 可独立回滚其卡片、身份解析与后端无 `device_id` 匹配分支，不影响仪表自身和直接连接 BMS OTA。
- 文档与看板状态同步回退。
- 本轮 ACK/队列修复可整体回滚移动端 OTA、BLE/MQTT transport 与轮询守卫，不回滚首页/扫码等无关变更，不涉及后端、数据库或固件协议。
- 9月3日超时推进试验已撤销，不属于可恢复的生产策略；如需回滚本轮页边界与重试实现，只能回到同包重发、全部数据ACK的上一稳定基线，不得恢复“超时跳包/末包缺ACK进入完成阶段”。重复十六进制日志精简可独立关闭，但有界内存、队列独占与完成条件不随之放宽。
- Android响应写优先、原生回调诊断与450ms读取探测可作为BLE transport单元整体回滚；回滚不得改变共享Boot游标、670ms同包重发、MQTT/4G或iOS策略。
